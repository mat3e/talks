C1: [System] Context Diagram
  • Big picture focus (people and systems rather than tech)
  • Shown also for non-tech people
Software system
  • Sth delivering value to its users (human or not)
  • Owned and built by a single dev team
✅ recommended for all dev teams
Supporting elements: people (e.g. users, actors, roles, or personas) and software systems (external dependencies) directly connected to the system in scope
C2: Container Diagram
  • Zoom in to the system boundary
  • High-level shape of the arch, distribution of responsibilities
  • Major technology choices, containers communication
Container
  • Application or data store. Not Docker!
  • Server-side web app, client-side SPA, desktop app, mobile app, database schema, folder on a file system, AWS S3 bucket, ...
✅ recommended (esp. for devs and operations)
C3: Component Diagram
  • Decomposes container into components
  • Responsibilities + technology/implementation details
Component
  • Groups and encapsulates functionality behind a well-defined interface
  • Container components execute in the same process space
❌ not recommended, automate the creation
C4: Code Diagram
  • Component implemented as code
  • UML class diagrams, entity relationship diagrams, similar
Code
  • Building blocks of the programming language
  • Classes, interfaces, enums, functions, objects, ...
❌ not recommended, to generate on-demand
  • Often available on-demand from tooling such as IDEs
  • Ideally automatically generated with tooling (IDE or UML modelling tool)
  • Show only those attributes and methods that allow you to tell the story that you want to tell
  • This level of detail is not recommended for anything but the most important or complex components
Supporting: System Landscape Diagram
  • Prev focus on a single software system
  • Systems never live in isolation
  • System Context Diagram w/o focusing on a particular system
  • Bridge into the enterprise architecture world
✅ recommended, esp. for larger organizations
Supporting: Dynamic Diagram
  • 2 styles: Collaboration or Sequence
  • Runtime collaboration (vs. prev static views)
  • User story, use case, feature, etc.
  • Can show software systems, containers, or components
❌ not recommended, just interesting/recurring patterns or features
Supporting: Deployment Diagram
  • Deployed systems and/or containers
  • Diagram per env
  • Deployment node = where an instance is running
  • Can contain infrastructure nodes: DNS services, load balancers, firewalls
  • Good idea to use icons (e.g. AWS)
✅ recommended

LikeC4

  • likec4.dev
  • Broader than C4, allows following C4 though
    1. Start by defining your grammar/DSL
    2. Build model with DSL
    3. Visualize model with views
  • Textual: versionable, LLM-friendly

Tests


                    import { describe, expect, it } from 'vitest'
                    import { $ElementKind, likec4model } from './likec4-model'

                    describe('view conventions', () => {
                      const views = [...likec4model.views()]

                      it('view IDs are kebab-case', () => {
                        const re = /^[a-z][a-z0-9]*(-[a-z0-9]+)*$/
                        const offenders = views.filter(({ id }) => !re.test(id)).map(({ id }) => id)
                        failIfExist(offenders, 'views with non-kebab-case IDs')
                      })

                      it('every view has a description or title', () => {
                        const offenders = views.filter(({ title, description }) => !title?.trim() && !description).map(({ id }) => id)
                        failIfExist(offenders, 'views without a title or description')
                      })
                    })

                    describe('element conventions', () => {
                      const elements = [...likec4model.elements()]

                      it('every (non-obvious) element has a description', () => {
                        const offenders = elements
                          .filter(e => !isTodo(e))
                          .filter(e => !hasDescription(e))
                          .map(({ id }) => id)
                        failIfExist(offenders, 'elements missing a description')
                      })

                      it('element name segments are camelCase', () => {
                        const re = /^[a-z][a-zA-Z0-9]*$/
                        const offenders = elements.filter(({ name }) => !re.test(name)).map(({ id }) => id)
                        failIfExist(offenders, 'elements with non-camelCase names')
                      })
                    })

                    describe('system conventions', () => {
                      const activeSystems = ofKind('system').filter(s => !isTodo(s))

                      it('every system owned by concrete folks', () => {
                        const offenders = activeSystems
                          .filter(s => !s.getMetadata('owner'))
                          .map(({ id }) => id)
                        failIfExist(offenders, 'systems missing metadata.owner')
                      })

                      it('every system has at least 2 containers (single-container systems are anti-pattern)', () => {
                        const offenders = activeSystems
                          .filter(s => [...s.descendants()].filter(d => d.isTagged('container')).length < 2)
                          .map(({ id }) => id)
                        failIfExist(offenders, 'systems with fewer than 2 containers — promote to a peer container or merge')
                      })

                      it('every system has a scoped view (`view ... of <system>`)', () => {
                        const offenders = activeSystems
                          .filter(s => s.scopedViews().size === 0)
                          .map(({ id }) => id)
                        failIfExist(offenders, 'systems without a scoped view — every system needs a container-level view')
                      })
                    })

                    describe('container conventions', () => {
                      const activeContainers = [...likec4model.elementsWhere({ tag: 'container' })].filter(s => !isTodo(s))
                      const activeDeployableContainers = ofKind('container').filter(s => !isTodo(s))

                      it('every container has a non-empty `technology`', () => {
                        const offenders = activeContainers
                          .filter(({ technology }) => !technology?.trim())
                          .map(({ id }) => id)
                        failIfExist(offenders, 'containers without `technology`')
                      })

                      it('every container has a tech `icon`', () => {
                        const offenders = activeContainers
                          .filter(({ icon }) => !icon)
                          .map(({ id }) => id)
                        failIfExist(offenders, 'containers without a tech `icon` — use `icon tech:<name>` (e.g. `tech:spring-icon`, `tech:postgresql`)')
                      })

                      it('every container links to its repository', () => {
                        const offenders = activeDeployableContainers
                          .filter(({ links }) => !links.some(({ title }) => title === 'Repository'))
                          .map(({ id }) => id)
                        failIfExist(offenders, 'containers not linking to `Repository` — each deployable should point at its Git repo')
                      })

                      it('every container is a direct child of system', () => {
                        const offenders = activeContainers
                          .filter(({ parent }) => parent?.kind !== 'system')
                          .map(({ id }) => id)
                        failIfExist(offenders, 'container/database/messaging/bucket must be a direct child of system — not under area/subdomain/domain, and not nested inside another container')
                      })
                    })

                    describe('component conventions', () => {
                      const activeComponents = [...likec4model.elementsWhere({ kind: 'component' })].filter(s => !isTodo(s))

                      it('every component is a direct child of container', () => {
                        const offenders = activeComponents
                          .filter(({ parent }) => !parent?.tags.includes('container'))
                          .map(({ id }) => id)
                        failIfExist(offenders, 'component must be a direct child of container/database/messaging/bucket')
                      })
                    })

                    const ofKind = (kind: $ElementKind) => [...likec4model.elementsWhere({ kind })]

                    const hasDescription = ({ description }: { description?: unknown }) => {
                      const d = description as { txt?: string; md?: string } | null | undefined
                      return !!d && (!!d.txt?.trim() || !!d.md?.trim())
                    }

                    const failIfExist = (offenders: string[], message: string) => {
                      const detail = offenders.length ? `\n  - ${offenders.join('\n  - ')}` : ''
                      expect(offenders, `${message}${detail}`).toHaveLength(0)
                    }

                    // #todo-tagged elements (and any element whose ancestor is #todo) are stubs —
                    // not yet fully defined. All quality-convention tests skip them.
                    const isTodo = (e: ReturnType<typeof ofKind>[number]): boolean => {
                      if (e.isTagged('todo')) return true
                      let p = e.parent
                      while (p) {
                        if (p.isTagged('todo')) return true
                        p = p.parent
                      }
                      return false
                    }

Model


                    model {
                      user = actor 'User' 'The one who wants to read fairy tales'

                      ft = system 'Fairy Tales' 'System for interacting with The Three Little Pigs or Little Red Riding Hood' {
                        metadata {
                          owner 'mat3e'
                        }

                        monolith = container 'Spring App' 'Entry point to the system, when CLI or HTTP mode can be chosen' {
                          link https://github.com/mat3e/3pigs-ddd/ 'Repository'
                          icon tech:spring-icon
                        }
                        container pigs3 {
                          title 'The Three Little Pigs'
                          description 'A fairy tale about pigs building their houses'
                          link https://github.com/mat3e/3pigs-ddd/ 'Repository'
                          icon tech:java
                        }
                        database pigs3db 'The Three Little Pigs H2 Database' 'DB schema - houses' {
                          icon tech:mysql-icon
                        }
                        container redhood 'Little Red Riding Hood' 'A fairy tale about listening to your mom, and not interacting with strangers' {
                          link https://github.com/mat3e/3pigs-ddd/ 'Repository'
                          icon tech:java
                        }
                        database redhoodDb 'Little Red Riding Hood H2 Database' 'DB schema - wolfs' {
                          icon tech:mysql-icon
                        }
                        messaging inMemBus 'In-memory events support' 'Spring way of exchanging events' {
                          icon tech:spring-icon
                        }

                        user -> monolith 'interacts with'

                        monolith -> redhood
                      }

                      extend ft.pigs3 {
                        monolith -> cli 'starts'
                        monolith -> rest 'interacts in HTTP mode via'

                        component cli 'Command-Line Runner' 'Runner printing a fairy tale in console' {
                          -> command 'executes commands in order'
                        }
                        component rest 'REST Controller' 'HTTP endpoints for interacting with houses' {
                          -> command 'creates/deletes houses via'
                          -> query 'reads houses via'
                        }
                        component command 'Command Handler' 'App logic for driving domain logic' {
                          -> factory 'creates new via'
                          -> wolf 'destroys with'
                          -> repo 'updates on diff via'
                        }
                        component event 'Event Handler' 'Executes commands based on incomming events' {
                          -> query 'finds house to escape via'
                          -> command 'calls'

                          inMemBus -[async]-> event 'triggers'
                        }
                        component query 'Query Repository' 'Allows to find closest houses and read models'
                        component wolf 'Wolf Service' 'Stateless work on house, encapsulating retrying logic' {
                          -> house 'tries to destroy'
                          -> blowing 'follows'
                          -[async]-> inMemBus 'informs when quitting'
                        }
                        component factory 'House Factory' 'Domain factory for creating house aggregate' {
                          -> building 'follows'
                          -> house 'creates'
                        }
                        component repo 'Repository' 'Allows to find by ID and save houses' {
                          -> house 'inserts/updates'
                          -> house 'reads'
                        }
                        component blowing 'Blowing Down Specification' 'Rules on when house can be destroyed by blowing'
                        component building 'Building Policy' 'Rules on how to build house depending on the character of a pig'
                        component house 'House Aggregate' 'DDD aggregate protecting rules about destroying and pig changes' {
                          -[async]-> inMemBus 'informs about refugees'
                        }
                      }
                    }

Views


                    views {
                      view index {
                        title 'Context'

                        include *
                        global predicate solidNonAsyncRel
                      }

                      view fairy-tales-index of ft {
                        title 'C4 / Containers'

                        include user
                        include ft
                        include * where kind is container
                        global predicate solidNonAsyncRel
                      }

                      view pigs3-index of ft.pigs3 {
                        title 'C4 / Components (The Three Little Pigs)'

                        include ft
                        include ft.* where kind is container
                        include *
                        include
                          -> house with {
                            multiple true
                          }
                        global predicate solidNonAsyncRel
                        global style mute_all
                        style ft.inMemBus {
                          color secondary
                        }
                        style ft.pigs3, ft.pigs3.** { color primary }
                      }
                    }

                    global {
                      predicateGroup solidNonAsyncRel {
                        include
                          * -> * where kind is not async with {
                            line solid
                          }
                      }

                      style mute_all * {
                        color muted
                        opacity 10%
                      }
                    }
